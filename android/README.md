# MiniAriño single-APK XFCE integration spike

This branch builds one ARM64 Android APK containing the MiniAriño UI, PRoot runtime, and embedded Lorie X11 server. On first desktop launch, the app verifies and extracts the pinned Debian Bookworm-slim ARM64 root filesystem into its private storage, installs XFCE and its applications from Debian's signed Bookworm repositories, starts Lorie with Debian's installed XKB data, launches the guest XFCE session, and opens the embedded display only after the session readiness gate succeeds. No Termux install, separate Termux:X11 app, QEMU, external terminal, or TUR is used.

This is still an **integration spike, not a device-verified XFCE desktop**. The Android emulator test exercises the target-SDK private-execution behavior and PRoot guest launch on Android API 35 using an x86_64 test fixture. It does not yet execute the production ARM64 PRoot on a phone, run Debian's ARM64 shell, install XFCE packages, test Lorie rendering/input, show all XFCE windows, or exercise physical-device lifecycle behavior. Do not describe the full desktop as working until those checks pass on the target phone.

## Why PRoot execution changed

The previous APK copied PRoot into writable app-private `files/linux/usr/bin/` and then called `chmod`. Android rejects `execve()` from an app's writable private data directory when the app targets API 29 or higher; setting executable mode does not remove that restriction. Termux retains target SDK 28 for this legacy execution behavior. MiniAriño now targets SDK 28 and stores/executes its Linux runtime within the app's own private directory, preserving the standalone single-APK design rather than copying PRoot to another app-private location or depending on another app.

This is an intentional sideloaded prototype tradeoff: target SDK 28 is below current Play Store submission requirements and may trigger Android's compatibility warning. The Android emulator instrumentation test checks the built target SDK on Android API 35, executes the packaged ARM64 PRoot from writable app-private storage, provisions the pinned Debian ARM64 rootfs, and requires `/bin/sh` inside that guest to print an exact success marker. That is the direct regression test for the reported `Permission denied` plus a real guest-execution check; a successful APK build alone is not treated as runtime proof.

## First desktop launch

1. Tap **Install XFCE desktop + start session** in MiniAriño. The app stays in MiniAriño while preparing the rootfs and installing packages; it does not show a blank display or report success early.
2. The app downloads, verifies, and extracts the pinned Debian ARM64 rootfs if needed, then launches PRoot to install `xfce4`, `xfce4-terminal`, `thunar`, and `dbus-x11` through Debian APT. The package installation also provides `/usr/share/X11/xkb`.
3. Lorie starts with `TMPDIR` pointing to MiniAriño's private shared temporary directory and `XKB_CONFIG_ROOT` pointing to the installed Debian keyboard data. MiniAriño waits for Lorie's private `:0` Unix socket before starting the guest session. PRoot binds that same temporary directory as Debian `/tmp` and starts the packaged XFCE session script.
4. The session script requires the installed commands and XKB files, starts a private D-Bus session, waits for `org.xfce.SessionManager`, and confirms Thunar, the XFCE terminal, and the session process remain alive. Only after the shared `MINIARINO_XFCE_SESSION_READY` marker does the app open the embedded Lorie activity.
5. Any failure leaves the user on MiniAriño's home screen with a short visible reason. The **Copy diagnostics** and **Share diagnostics** buttons include the failure and recent installer, XFCE, and X11 logs; the user does not need a separate terminal or to hunt through private storage. **Stop MiniAriño session** signals the tracked PRoot and Lorie processes.

The first rootfs download and APT installation require network access and substantial free app-private storage. Debian package revisions can change as the Bookworm suite receives updates. Rootfs layers, extracted system files, package state, scripts, and logs remain in app-private storage; user-selected shared folders continue to use Android's Storage Access Framework.

## Runtime design and pinned inputs

- ABI/userland: Android ARM64 (`arm64-v8a`) and Debian ARM64 on the Android host kernel.
- PRoot: Termux package `5.1.107.96`, source/build metadata commit [`de39661946f7e8175b5dd0755121fa28cb0aebd1`](https://github.com/termux/termux-packages/commit/de39661946f7e8175b5dd0755121fa28cb0aebd1). Fixed ARM64 package URLs, SHA-256 checks, architecture checks, and APK asset staging are in `scripts/fetch_proot_runtime.py`. PRoot is GPL-2.0; `libtalloc` is GPL-3.0; `libandroid-shmem` is BSD-3-Clause. License texts are bundled under `app/src/main/assets/proot-licenses/`.
- Debian: official Docker Library `debian:bookworm-slim`, ARM64 OCI manifest `sha256:a1b86db52ce3daef089e45aabe36dfec4091f82464c25c1fdcf03de197cbe82a`; the app verifies its manifest hash and expected one-layer descriptor. The 28,137,179-byte compressed layer must match `sha256:c75f989a229d12b2d2613a5997de9ff3546f664c22da9248720033a2410220f6` before extraction.
- Private-storage runtime: the PRoot binary and its host libraries are copied into `getFilesDir()` and executed there under the app's target SDK 28 compatibility behavior. Debian guest files are also private app data; the smoke test exercises a real guest ELF rather than only `proot --version`.

## What passing CI verifies

The workflow builds the single ARM64 debug APK, checks package identity, target SDK 28, ARM64 native libraries, pinned ARM64 PRoot assets/licenses, Debian package availability, shell syntax, startup wiring, and APK SHA-256. It also stages the exact Termux PRoot 5.1.107.96 package for x86_64 **only in the Android instrumentation-test APK**. The workflow boots an Android API 35 x86_64 emulator and runs `:app:connectedDebugAndroidTest`. The test asserts the target app's SDK is 28, copies x86_64 PRoot and its pinned host dependencies from test assets into writable app-private storage, sets executable mode, and starts that PRoot there. PRoot then runs `/system/bin/sh` through a minimal synthetic guest root with `/system` and `/apex` bound in, and the test requires the guest command's exact `MINIARINO_PROOT_GUEST_OK` output. The app APK artifact is uploaded only after this runtime test succeeds.

This is a genuine Android `execve`/PRoot/guest-process test on API 35, not an APK-build-only assertion; it proves the target-SDK compatibility path in an Android process. Its host binary is x86_64 because Google's current Android emulator workflow uses supported x86/x86_64 emulator images; it does **not** execute the production ARM64 PRoot or a Debian ARM64 guest. The emulator test also does not install XFCE packages, start Lorie, check the X socket or keyboard input, open the XFCE display, or prove a physical phone's SELinux/kernel behavior and lifecycle. Those remain required device checks: install/update on the target ARM64 Android version, confirm ARM64 PRoot and Debian guest execution, complete first-run APT installation, confirm the XFCE session manager and terminal/file-manager windows, verify keyboard/mouse input and app switching, stop/restart, and repeat after pause/process reclaim. Godot, Chromium, and Blender are not part of this milestone.

## Updating an APK already installed

A debug APK signed by a different key cannot replace an installed build; Android reports a signature mismatch. The earlier candidate was also a workflow-built debug APK, and its signing certificate has not been verified against this build. Do not uninstall it just to work around an update error: uninstalling deletes MiniAriño's private Debian rootfs, installed packages, workspace, and logs. Preserve or export anything needed before considering an uninstall/reinstall. This prototype does not claim a stable release signing key.
